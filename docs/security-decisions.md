# Security decisions

1. **One static executable on scratch.** The service requires no OS packages or trust bundle. CGO is disabled; a missing-shell integration test and archive inspection verify the layout. A future HTTPS client would need an explicitly managed trust bundle and egress policy.
2. **No external Go modules.** `go.mod` pins the compiler minimum to an exact patched version; the pipeline requires that exact version. There is no `go.sum` because there are no external modules. `go list -m all` must contain only this module, `-mod=readonly` prevents implicit edits, and `GOPROXY=off`, `GOTOOLCHAIN=local` prevent fetches. Disabling the checksum service is safe only under this zero-dependency contract; restore checksum verification before intentionally adopting dependencies.
3. **Reproducibility includes layers.** `-trimpath -buildvcs=false -ldflags='-s -w -buildid='`, epoch zero and `rewrite-timestamp=true` remove variable paths, VCS metadata, build IDs and filesystem timestamps. BuildKit provenance and automatic SBOM output are disabled to avoid variable image-index entries. The project publishes its own signed SBOM and explicitly scoped evidence; it does not claim a SLSA level.
4. **Narrow chart contract.** JSON-as-YAML avoids a manifest parser dependency. Policy requires the expected four resource kinds and validates the security-relevant fields and selectors. Arbitrary YAML, CRDs, RBAC, init containers, sidecars, volumes and environment injection are outside the supported contract.
5. **Fail closed with visibility.** A scanner error, stale database, missing inventory, image mismatch or malformed finding fails the gate. All findings remain in the raw report; LOW and MEDIUM do not block by default. HIGH can have a short-lived scoped exception; CRITICAL and unknown severities cannot. No ignore file or VEX suppression is used.
6. **Different release capabilities in different jobs.** Quality can read source. Publishing can write packages and request an identity token, but cannot write source. A separate final job can create release records with contents write. Action references are commit-pinned; checkout credentials are not persisted. There is no pull-request-target trigger or long-lived signing secret. The repository defaults workflow tokens to read-only and requires the `checks` status on `main`; force pushes and branch deletion are disabled. Repository administrators retain an explicit bypass, consistent with the trusted-maintainer boundary.
7. **Verification precedes deployment.** The helper requires a full digest, exact semantic version tag, expected workflow identity and expected OIDC issuer. It verifies image, SBOM and evidence attestations. Consumers deploy that exact digest. A separate, pinned admission-controller installation now enforces the exact release signer and issuer in enrolled namespaces, with no-match denial and fail-closed webhooks. The application chart does not grant itself cluster-wide verifier installation rights; see [admission verification](admission-signatures.md).

## Updating locked inputs

Use a separate reviewed change. Resolve the new release's published checksums over HTTPS, compare the downloaded bytes, and update `tools.lock.json`. Lock hashes establish byte stability after selection; they are not an independent upstream signature-verification system. `checksumSource` records where each published hash was checked.

For a compiler update, change the Go entry in the tool lock, `go.mod`, the exact-version assertion in the Makefile, and the builder tag **and index digest** in the Dockerfile together. `check-inputs.py` rejects inconsistent compiler pins. Regenerate tools with `make tools`, then run `make check`, the local signing exercise and `make cluster`. Record live before/after scan details and preserve previous evidence if the update is a remediation.

The builder digest controls compiler image bytes, while tool-download checksums control the local test compiler and auxiliary CLIs. BuildKit 0.30.0 is also pinned by image digest and runs in a disposable builder removed after each build. The host engine, C compiler, Make, Python, runner image and cryptographic trust/database services are operational inputs, not fully hermetic dependencies. Rebuild equality is asserted within one configured environment.

## Runtime network-policy test boundary

The application image and chart stay unchanged. A two-node disposable cluster installs the pinned `kube-network-policies` agent in its system namespace. That infrastructure agent needs node networking privileges and narrowly scoped list/watch access to pods, namespaces and policies. It is a test dependency, not an application sidecar or a chart resource. The chart's workload remains non-root with a read-only root filesystem.

The test-only Go client is copied into the disposable nodes and launched with `nsenter --net` against each pod sandbox PID. It verifies the expected pod IP exists in that namespace and binds that IP explicitly. This tests actual packet filtering without installing a shell, client, debug container or writable volume into the workload. Administrative access is used to instrument only the created cluster; it is not an application capability. Full methodology, controls and scope are in [the runtime verification](network-policy.md).

## Admission trust and availability

The API-server controller verifies real signatures with normal certificate/log checks, rather than implementing custom cryptography or trusting a repository-name prefix. Both production trust policies use an exact issuer and workflow subject. Independent policies require the image signature and both authenticated SBOM/evidence predicates; mandatory predicate content checks are described in [the attestation guide](admission-attestations.md). Unknown images are denied in enrolled namespaces, and the test changes trust after a successful admission to verify cache invalidation. The webhook's writable home is an empty directory for trust-root cache initialization; its container is non-root, read-only elsewhere, with privilege escalation disabled and capabilities dropped. TLS material is generated at runtime and kept inside the cluster.

The negative-fixture registry and its CA exist only during the disposable test. The test temporarily redirects the attestation authority to generated public-key trust, preserving both predicate policies and the independent real release-signature policy. Its synthetic report references are not vulnerability evidence. Production keyless trust is restored and tested before the availability fault. No production policy contains a fixture key, alternate registry or transparency bypass.

The outage test stops the verifier's runtime task only in a fresh disposable cluster, confirms the process and Service endpoints are gone, and checks that the API server rejects even a previously verified image. Out-of-scope requests remain an API-liveness control, and the restored controller must admit the trusted image again. Namespace enrollment and cluster-wide policy/webhook configuration remain administrator-controlled boundaries.

## Current trust during admission

The dedicated verifier build reads current CIPs directly, preserves the existing cryptographic checks, and rejects a detected state change before allowing. It requires both mandatory policy objects and rejects mutable referenced trust sources rather than consulting stale copies. Plain status updates and pure replica reduction remain available; combining scale-down with a template or label change invokes current policy validation. The exact in-flight boundary, deployment migration requirements and supported policy profile are recorded in [the trust-update guide](trust-updates.md).
