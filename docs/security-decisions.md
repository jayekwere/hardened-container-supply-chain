# Security decisions

1. **One static executable on scratch.** The service requires no OS packages or trust bundle. CGO is disabled; a missing-shell integration test and archive inspection verify the layout. A future HTTPS client would need an explicitly managed trust bundle and egress policy.
2. **No external Go modules.** `go.mod` pins the compiler minimum to an exact patched version; the pipeline requires that exact version. There is no `go.sum` because there are no external modules. `go list -m all` must contain only this module, `-mod=readonly` prevents implicit edits, and `GOPROXY=off`, `GOTOOLCHAIN=local` prevent fetches. Disabling the checksum service is safe only under this zero-dependency contract; restore checksum verification before intentionally adopting dependencies.
3. **Reproducibility includes layers.** `-trimpath -buildvcs=false -ldflags='-s -w -buildid='`, epoch zero and `rewrite-timestamp=true` remove variable paths, VCS metadata, build IDs and filesystem timestamps. BuildKit provenance and automatic SBOM output are disabled to avoid variable image-index entries. The project publishes its own signed SBOM and explicitly scoped evidence; it does not claim a SLSA level.
4. **Narrow chart contract.** JSON-as-YAML avoids a manifest parser dependency. Policy requires the expected four resource kinds and validates the security-relevant fields and selectors. Arbitrary YAML, CRDs, RBAC, init containers, sidecars, volumes and environment injection are outside the supported contract.
5. **Fail closed with visibility.** A scanner error, stale database, missing inventory, image mismatch or malformed finding fails the gate. All findings remain in the raw report; LOW and MEDIUM do not block by default. HIGH can have a short-lived scoped exception; CRITICAL and unknown severities cannot. No ignore file or VEX suppression is used.
6. **Different release capabilities in different jobs.** Quality can read source. Publishing can write packages and request an identity token, but cannot write source. A separate final job can create release records with contents write. Action references are commit-pinned; checkout credentials are not persisted. There is no pull-request-target trigger or long-lived signing secret.
7. **Verification precedes deployment.** The helper requires a full digest, exact semantic version tag, expected workflow identity and expected OIDC issuer. It verifies image, SBOM and evidence attestations. Consumers must then deploy that exact digest; the Helm chart itself does not verify signatures.

## Updating locked inputs

Use a separate reviewed change. Resolve the new release's published checksums over HTTPS, compare the downloaded bytes, and update `tools.lock.json`. Lock hashes establish byte stability after selection; they are not an independent upstream signature-verification system. `checksumSource` records where each published hash was checked.

For a compiler update, change the Go entry in the tool lock, `go.mod`, the exact-version assertion in the Makefile, and the builder tag **and index digest** in the Dockerfile together. `check-inputs.py` rejects inconsistent compiler pins. Regenerate tools with `make tools`, then run `make check`, the local signing exercise and `make cluster`. Record live before/after scan details and preserve previous evidence if the update is a remediation.

The builder digest controls compiler image bytes, while tool-download checksums control the local test compiler and auxiliary CLIs. The host engine, BuildKit, C compiler, Make, Python, runner image and cryptographic trust/database services are operational inputs, not fully hermetic dependencies. Rebuild equality is asserted within one configured environment.
